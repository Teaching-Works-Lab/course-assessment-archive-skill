# 受控自我更新

## 什么时候使用

- 收到新版、补充、替换或盖章后的制度文件；
- 文件名未变但哈希、页数或附件发生变化；
- 用户指出回答、目录、角色或依据有误；
- 用户要求重新摄入或刷新规则。

自我更新表示 Skill 知道如何重新读取证据并形成修改，不表示它可以静默改写自己、接受未经核验的口头规则或自动推送 GitHub。

## 1. 登记原件和版本

1. 保存原文件，不覆盖旧版本；记录真实路径、文件名、文号、日期、页数和 SHA-256。
2. 区分原始来源、转换产物、分析结果和正式 Skill 文件。
3. 判断新文件是替代、补充、局部修订还是来源不明。没有废止或替代证据时，保留版本冲突。
4. 原始 PDF 和学生级材料不复制进 Skill；用户指定了记录位置时，只保存可追溯路径和去身份化结论；未指定时仅在答复中给出记录草案。

## 2. 从 PDF 提取文字和页面

先按变化类型选择最小处理范围：

- 只改错别字、表达或已确认的文件名：核对受影响条款和引用，不重新拆整份 PDF；
- 新增或修改普通文字条款：本地 PDF 首轮使用本机 `markitdown` 转为 Markdown，并重点复核相关页；
- 扫描页、复杂表格、目录截图、附件图像、红色批注或图文冲突：再逐页渲染并执行完整图像拆分。

需要完整处理时，保留 MarkItDown 输出作为机器提取层，并把相关页面渲染为 PNG，核对标题、页码、表格、盖章、批注、箭头和截图路径。

MarkItDown 提取结果不能替代原 PDF：扫描页、复杂表格、目录截图和红色批注以渲染页及原图复核。

## 3. 拆分图像

必须分别记录两种数量：

- **原始图片对象**：PDF 内实际嵌入的位图对象，原样保存；
- **语义图片**：为了独立阅读而从原图或渲染页裁出的真实图像文件，一个逻辑节点、表格分段或批注目标一张图。

语义图片不是抽象总结。每张语义图片都要保存文件，并记录原页、父原图、裁剪范围、可见文字和它与相邻图片的关系。

按附件类型处理：

- 连续目录截图：用面包屑路径连接前后图；同时按学院、专业、课程、教师教学班、材料分支和具体材料拆分；
- 矢量表格：没有位图对象时，保留整表渲染，再按有意义的行组分段，不虚构“原始图片”；
- 带箭头批注的报告：保留完整批注图，再按每个箭头或批注目标分别裁图；
- 一张原图含多个逻辑节点时，原图数量和语义图数量可以不同，二者不得混报。

OCR 或人工转写后仍要看图确认文字、箭头起止、红框范围、父子路径和表格合并关系。批注属于解释层，不把红框、箭头文字误当成正式文件名。

## 4. 编译为可追溯规则

每条归纳结果标记为：

- 原文明确；
- 图像明确；
- 原文与图像共同支持；
- 合理推断；
- 冲突；
- 待确认。

先还原文件自身结构，再转成业务结构：

```text
文号与适用范围
→ 目录层级及父子关系
→ 正考/补考与试卷/非试卷两个分类轴
→ 每个材料的目录位置和命名
→ 任课教师、课程负责人、专业/教学秘书、学院的责任
→ 创建、提交、退回、复核和验收关系
```

不能从示例姓名、示例课程、截图偶然扩展名或未标注区域推导普遍强制规则。

## 5. 评价是否可用

编译结果只有同时回答以下问题才算“可用”：

1. 谁负责建立这一层、谁提供材料、谁复核？
2. 每类文件应放在哪一级、哪个分支、使用什么名称？
3. 考试课、非试卷课、正考和补考怎样分流？
4. 目录正确之外，还需要哪些评分、签字和学生证据？
5. 每项结论能否回到页码、正文、原图或语义图？
6. 冲突和无法确定的问题是否显式保留？

评价只使用三档：`可用`、`可用但有待确认项`、`不可用，需补证`。不使用没有明确意义的综合分数。

## 6. 形成更新预览

比较新证据与现有内容，列出：新增、修改、废止、冲突、受影响角色、受影响问答和回归场景。按内容性质更新：

| 内容 | 更新位置 |
| --- | --- |
| 原文转写、页图和附件图 | 用户指定的证据目录；不得放入公开 Skill 包 |
| 附件关系和跨页解释 | 用户指定的分析记录位置 |
| 现行制度与角色责任 | `references/current-rules-and-roles.md` |
| 已确认错误和常见问答 | `references/common-errors-and-qa.md` |
| 更新方法本身发生变化 | 本页或 `SKILL.md` |
| 反馈状态和迭代结果 | 用户指定的反馈记录；没有指定时在答复中给出记录草案 |

先展示修改预览。只有用户已明确要求更新，且来源、影响和边界已经核清，才写入 Skill 或用户指定的记录位置。遵守目标位置自身的组织规则，不猜测路径。

## 7. 反馈和纠错

每条反馈登记：日期、提出者角色、原问题、原回答或错误、用户提供的依据、证据状态、影响范围和处理状态。

状态使用：`待核验` → `已确认` / `不成立` → `已应用` → `已回归`。

- 正式文件支持的错误：修正规则和受影响问答；
- 新旧来源冲突：保留双方并标记冲突，不静默覆盖；
- 用户表达偏好：只调整回答方式；
- 没有证据的口头做法：保留为待核验，不进入强制规则。

## 8. 最小验证和发布

更新后只做与改动相称的验证：

1. 用导致本次更新的真实问题重跑一次；
2. 检查是否影响相邻角色和课程分支；
3. 运行 Skill 格式验证；
4. 记录结果和仍待确认项。

GitHub 发布是独立外部动作。可以准备 diff、提交说明、来源摘要和回滚点；只有用户明确授权并确认仓库范围后才能提交或推送。原 PDF、学生信息和未脱敏材料不得因发布 Skill 而上传。

发布采用白名单：只允许 `SKILL.md`、`agents/openai.yaml` 和 `references/*.md`。提交前检查 staged diff；出现 PDF、图片、知识库页面、学生名册、成绩、答卷、未脱敏附件或本机绝对路径时立即停止发布，除非用户另行完成脱敏并明确授权。
